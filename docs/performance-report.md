# 性能評価

## 測定条件

2026年10月18日、macOS / Apple M1 / メモリ8GB、Microsoft Edge 155.0.4283.62、headlessで測定しました。Windows/IISの数値ではありません。各条件1回の観測で、平均・上限保証ではありません。ほかの作業がある端末上の測定です。

専用テストは `tests/performance/`、測定JSONは `docs/validation/` にあります。XMLはテストで生成した合成データだけを使用しました。1～500MiBは100個のItemを持つGroupを繰り返し、各Itemに4000文字を格納しています。100万要素は空のItemを1000個持つGroupを1000個並べた別の構造です。

## 解析・表示・検索

| 入力規模 | 実バイト数 | 要素数 | 読込全体 秒 | 解析部分 秒 | DB保存待機 秒 | グラフ 秒 | 名前検索 秒 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 約1MiB | 1,206,349 | 304 | 0.57 | 0.21 | 0.21 | 0.21 | 0.03 |
| 約10MiB | 10,857,054 | 2,728 | 2.33 | 1.05 | 1.24 | 0.11 | 0.08 |
| 約100MiB | 104,951,657 | 26,362 | 23.13 | 10.14 | 12.78 | 0.62 | 0.69 |
| 約500MiB | 524,356,863 | 131,705 | 201.05 | 44.74 | 156.10 | 1.20 | 2.53 |
| 100万要素 | 7,015,013 | 1,001,001 | 418.29 | 18.37 | 399.69 | 1.45 | 8.45 |

1～100MiBはPlaywrightの一時コンテキスト、500MiBと100万要素は専用の保存用プロファイルを使用しました。ユーザーの通常プロファイルは変更していません。グラフは表示上限500ノードの部分描画です。検索はGroup完全一致です。

読込全体はファイル指定からUI完了まで。解析部分はDB待機を除く経過時間、DB保存待機にはノード・テキスト・索引等の保存を含みます。純粋なCPU時間や索引構築だけの時間ではありません。

| 入力 | 画面側JSヒープの観測最大 MB | IndexedDB使用量 MB |
|---|---:|---:|
| 1MiB | 3.07 | 1.50 |
| 10MiB | 7.70 | 12.81 |
| 100MiB | 16.04 | 123.63 |
| 500MiB | 3.46 | 202.58 |
| 100万要素 | 5.97 | 399.29 |

この表のMBは10進です。ヒープは250ms間隔の `performance.memory` の参考値で、Worker・ブラウザ内部・OS・GPUを含みません。GCや計測公開粒度に左右され、500MiBの方が小さいことをアプリ全体の低メモリ保証とは解釈できません。全プロセスの最大メモリは未測定です。IndexedDBはブラウザの使用量推定値で、反復文字列の圧縮・保存方式にも左右されます。

## 100MiBの比較とXLSX

各104,951,657バイトのXMLを2つ読み込み、1つのテキスト値だけを変更して比較しました。2ファイルの読込全体52.38秒、比較のUI所要0.328秒、Worker内0.202秒。MODIFIED 1、UNCHANGED 52,461、ほか0を確認しました。完全比較・空白保持・コメント/PIを含む設定で、SHA-256による一致サブツリーの省略が有効です。大部分が一致するこのケースを、全面変更や曖昧な大量兄弟の比較速度に一般化できません。

別途100MiBの同一ファイル比較は0.029秒、26,100行（idとSourceFile）のXLSX生成は7.03秒でした。後者は生成バッファ完成までで、Excel起動時間を含みません。無制限のXLSX出力は保証せず、5万行・50万セル・1600万文字の上限を設けています。

## 失敗と改善

- 一時コンテキストで500MiBと100万要素がSTORAGE_FULLになりました。100万要素は61.39秒で停止し、部分データの削除を確認しました。専用の保存用プロファイルでは両方とも解析・表示・検索に成功しました。実際に利用可能な保存容量はブラウザ状態・ディスク・ポリシーに依存し、表示されたquotaだけでは成功を保証できません。失敗の内部原因はブラウザ実装まで特定していません。
- 100万要素はDB保存待機が全体の約96%を占めました。索引・ハッシュの保存重複削減やバッチ設計の見直しが改善候補です。
- 最初の保存用プロファイル測定では、全データ削除が120秒以内に完了せずテスト全体が失敗しました。上表の解析・検索成功と削除失敗を区別しています。全ストアを順次clearする方式から、専用DBの削除と画面再読込に変更しました。再測定結果は本書末尾に記録します。
- 操作テストでツリー領域が行数に合わせて伸びる不具合を修正しました。600件の入力に対してDOMの描画行数を50未満に保つテストが通っています。

## 再実行

```sh
npm ci
npm run build
npm run test:performance
# 保存用の隔離プロファイルで拡張検証（macOS/Linux）
PERF_CASE=500,million PERF_PERSISTENT=1 npm run test:performance
PERF_CASE=pair npm run test:performance
PERF_CASE=csv npm run test:performance
```

PowerShellでは `$env:PERF_CASE='500,million'; $env:PERF_PERSISTENT='1'; npm run test:performance` とします。検証後はそのシェルで設定した環境変数を解除してください。合成XML・JSONはoutput/performanceに生成され、通常完了時は合成XMLと専用ブラウザプロファイルを削除します。

## 削除修正後の再測定と大容量CSV

同じ100万要素を保存用の隔離プロファイルで再実行し、読込405.49秒（解析21.33秒、DB待機383.75秒）、グラフ1.32秒、検索8.22秒、全データ削除0.204秒で完了しました。削除後の再読込と0ファイル表示までテスト成功です。データベースの論理的な削除を確認したもので、OSディスク上の物理的な完全消去を保証するものではありません。画面側ヒープ観測最大3.65MB、保存量推定385.65MBでした。証跡は `validation/performance-million-fixed.json` です。

10,500行、42,282,916バイトのCSVを5.92秒で逐次生成・保存し、末尾のid=10499を確認しました。FileSystemWritableFileStreamの実書き込みをOPFSで検証し、ネイティブの保存ダイアログ部分はテスト用に置換しています。Windowsの保存ダイアログ、任意の保存先の権限やディスク不足は未検証です。証跡は `validation/performance-csv.json` です。
